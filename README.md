# Heatpump Monitor

A personal learning project inspired by remote maintenance platforms for heat pumps.

The application stores simulated temperature and pressure measurements and displays them in a React dashboard. It is an independent demo with no company affiliation.

## Features

- Device overview with names, locations and demo statuses
- REST API for submitting and retrieving measurements
- PostgreSQL persistence
- Temperature and pressure chart with separate, colour-matched axes
- Chart legend and a dashed pressure line
- Automatic measurement refresh every 10 seconds
- Manual refresh and loading, empty and error states
- Spring Boot Actuator health endpoints

## Technology stack

- Backend: Kotlin, Spring Boot, Gradle, Spring Data JPA
- Database: PostgreSQL 17
- Frontend: React, TypeScript, Vite, Recharts
- Container environment: Docker Compose for frontend, backend and database

## Architecture

The React dashboard communicates with the Kotlin REST API through Nginx in Docker, or through the Vite proxy during local development. The backend reads and writes measurements in PostgreSQL.

The frontend, backend and PostgreSQL database run in separate Docker containers. Nginx serves the dashboard and forwards API requests to the backend.

## Run the full application with Docker

Start Docker Desktop, then run from the project root:

```powershell
docker compose up -d --build
```

The first build downloads dependencies and may take several minutes.

- Dashboard: http://localhost:8082
- Backend API: http://localhost:8081/api/devices
- Backend health: http://localhost:8081/actuator/health
- PostgreSQL host port: 5433

All three services run in Docker. No separate `bootRun` or `npm run dev` process is needed for this mode.

Check service status:

```powershell
docker compose ps
```

Inspect backend logs:

```powershell
docker compose logs --tail=100 backend
```

Stop the application:

```powershell
docker compose stop
```

Database data is stored in a named Docker volume and survives container recreation.

## Submit a demo measurement

With the backend running, execute this in a free PowerShell window:

```powershell
$sample = @{
    temperatureCelsius = 47.2
    pressureBar = 2.1
} | ConvertTo-Json

Invoke-RestMethod -Method Post `
    -Uri "http://localhost:8081/api/devices/1/measurements" `
    -ContentType "application/json" `
    -Body $sample
```

Select **Heatpump A** in the dashboard. The measurement should appear on the next automatic refresh.

A fresh database contains four demo devices and no measurements.

## API

| Method | Path | Description |
|---|---|---|
| GET | `/api/devices` | List devices |
| GET | `/api/devices/{id}` | Get a device; 404 if unknown |
| POST | `/api/devices/{id}/measurements` | Store temperature and pressure |
| GET | `/api/devices/{id}/measurements` | Get up to 100 latest measurements, newest first |
| GET | `/actuator/health` | Application health |
| GET | `/actuator/health/liveness` | Liveness health |
| GET | `/actuator/health/readiness` | Readiness health |

Measurement timestamps are generated by the backend and returned in UTC. The dashboard displays them in the browser's local time.

## Validation

Temperature and pressure are required and must be finite numbers. Pressure must be non-negative. Unknown devices return 404.

These are basic input checks, not manufacturer-specific operating limits.

## Rule-based demo alerts

`GET /api/devices/{deviceId}/alerts` evaluates the latest measurement using these demo rules:

| Code | Condition |
| --- | --- |
| HIGH_TEMPERATURE | Temperature > 60 °C |
| LOW_PRESSURE | Pressure < 1 bar |
| HIGH_PRESSURE | Pressure > 3 bar |

Values exactly at the thresholds do not trigger alerts. These thresholds are illustrative and are not technical operating limits for real equipment.

The response includes the evaluated measurement ID, its timestamp and the current alerts. For a device without measurements, the measurement ID and timestamp are null. An unknown device returns HTTP 404.

Alerts are calculated on request and are not stored as an alert history. A new normal measurement clears current alerts. Older abnormal measurements remain in the measurement history.

The dashboard refreshes alerts every ten seconds and displays the evaluated measurement timestamp. Alert loading errors are shown separately from measurement loading errors. Device statuses remain fixed demo values.

### Run alert unit tests

From the repository root:

```powershell
.\backend\gradlew.bat -p .\backend test --tests "at.demo.heatpump.device.AlertServiceTest"
```

These tests do not require a database.

### Manual verification

Verified in the local Kubernetes demo:

- A device without measurements returns null measurement metadata.
- Temperature 70 °C and pressure 3.5 bar trigger both high-temperature and high-pressure alerts.
- A subsequent measurement of 45 °C and 2 bar clears the alerts.
- The dashboard displays and clears these alerts automatically without a page refresh.

## Local Kubernetes demo with kind

This setup runs PostgreSQL, the backend, the frontend and the synthetic measurement simulator in a local kind cluster.

Requirements: Docker Desktop running with Linux containers, kind and kubectl. Run the commands from the repository root.

### Build the application images

```powershell
docker build -t heatpump-monitor-backend:latest ./backend
docker build -t heatpump-monitor-frontend:latest ./frontend
docker build -t heatpump-monitor-simulator:latest ./simulator
```

### Create the cluster

Run this once. Skip it if the cluster already exists.

```powershell
kind create cluster --name heatpump-monitor --wait 120s
```

### Load the local images

```powershell
kind load docker-image heatpump-monitor-backend:latest heatpump-monitor-frontend:latest heatpump-monitor-simulator:latest --name heatpump-monitor
```

The application deployments use `imagePullPolicy: Never` to use images loaded into kind. PostgreSQL uses the public `postgres:17` image.

### Deploy the application

```powershell
kubectl --context kind-heatpump-monitor apply -f ./k8s/00-namespace.yaml
kubectl --context kind-heatpump-monitor apply -f ./k8s/01-database.yaml
kubectl --context kind-heatpump-monitor -n heatpump-monitor rollout status deployment/database --timeout=180s
kubectl --context kind-heatpump-monitor apply -f ./k8s/02-backend.yaml
kubectl --context kind-heatpump-monitor -n heatpump-monitor rollout status deployment/backend --timeout=300s
kubectl --context kind-heatpump-monitor apply -f ./k8s/03-frontend.yaml
kubectl --context kind-heatpump-monitor -n heatpump-monitor rollout status deployment/frontend --timeout=120s
kubectl --context kind-heatpump-monitor apply -f ./k8s/04-simulator.yaml
```

The backend connects to PostgreSQL through the internal `database` Service. Nginx forwards frontend `/api/` requests to the internal `backend:8080` Service.

The backend uses Spring Boot Actuator startup, readiness and liveness probes.

### Open the dashboard

```powershell
kubectl --context kind-heatpump-monitor -n heatpump-monitor port-forward --address 127.0.0.1 service/frontend 8083:80
```

Keep this terminal open and visit http://localhost:8083.

Select Heatpump A or Heatpump B to view synthetic measurements. The dashboard polls every ten seconds. Press Ctrl+C to stop port-forwarding; the workloads continue running.

### Check workloads and storage

Run these commands in another terminal:

```powershell
kubectl --context kind-heatpump-monitor -n heatpump-monitor get pods,pvc
kubectl --context kind-heatpump-monitor -n heatpump-monitor logs deployment/simulator --tail=20
```

PostgreSQL uses a 1Gi PersistentVolumeClaim with kind's `standard` local-path StorageClass. The volume survives replacement of the database Pod within the existing cluster.

The Kubernetes database is separate from the Docker Compose database. Existing Compose data is not automatically transferred.

This storage is intended for a local demo. Deleting the PVC or kind cluster can remove the database data. The database credentials in the manifests are local demo values.

### Stop or restart the simulator

```powershell
kubectl --context kind-heatpump-monitor -n heatpump-monitor scale deployment/simulator --replicas=0
```

Restart it with:

```powershell
kubectl --context kind-heatpump-monitor -n heatpump-monitor scale deployment/simulator --replicas=1
```

This is a learning and portfolio project, not a production deployment. Measurements are synthetic, and device statuses are fixed demo values.
